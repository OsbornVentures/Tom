# Tom 0.5.0 development evaluation

This is an unsigned development build, not a qualified shipping release. Browser subject drift, visible failures and capability explanations have improved. Live weather and longer webpage tasks still fail in the recorded evaluation.

## What changed

Conversational questions about changing facts now require a browser attempt. Short follow-ups recover their subject from earlier user messages. The first search query is constrained during decoding, and relevance checks compare identifying words, region codes and product numbers against the user's subject. General words such as “weather” and “today” cannot make Arlington a match for Lorena TX. These are general rules, with no city-specific production code.

Failed searches record provider outcomes and retain the original query in an explicit browser recovery button. Tom no longer spends additional model turns claiming that it lacks web access after a provider failure. Opening the search in the user's normal browser is a user action; results still need to be attached or read before Tom can verify an answer. A browser challenge is not bypassed.

The favicon has a new emerald/cyan design and a new URL to avoid the cached orange icon. Actual errors appear red; blocked, review and loop states remain amber. Help illustrates nine avatar states and explains actions, model limits, memory and context. The mobile Help button is visible. Context is described as shared space for the request, results and reply, with tokens explained as small text pieces. The UI explains why available RAM is also needed by the model, images, browser, Windows and other apps.

E2B is described as a small local model suited to short, clear requests. The shell/write harness and structured protocol remain shared across model packages. Only the pinned E2B package is evaluated here. Other Gemma 4 or future packages need a compatible runtime, matching vision projector where applicable, and their own local qualification. Strict grammar controls response structure; it does not guarantee correct facts or successful tasks.

## Recorded outcomes

The [development candidate](candidate-0-5-0.md) passed **4 of 9 planned checks**. Its webpage task reached the ten-minute limit after five compactions, so its follow-up was skipped and counted as failed. Its documentation search exposed an overstrict relevance rule; that rule was corrected before the final browser regression. The candidate is preserved as a development result, not presented as the final production baseline.

The [final browser regression](browser-0-5-0.md) used the final production harness and UI and passed **3 of 5 checks**:

| Case | Outcome | Wall time |
|---|---|---:|
| Two-page browsing | Passed; read both sources and verified requested facts | 80.2 s |
| Missing page | Passed negative test; reported the HTTP failure | 36.3 s |
| Conversational Lorena weather | Failed task; correct query, honest provider blocker | 23.8 s |
| Weather follow-up | Failed task; retained Lorena, honest provider blocker | 31.1 s |
| Live documentation search | Passed; searched and read MDN localStorage and setItem pages | 224.5 s |

Both weather tasks searched for Lorena TX and read no Arlington pages. DuckDuckGo requested human verification in the isolated automated browser; Bing returned no matching sources. The user's normal Edge session could display relevant DuckDuckGo weather results, but this does not establish that a clean automated session can do so. Weather remains an end-to-end failure. Honest containment is useful but does not count as answering the question.

The final relevance rule allows documentation discovery when a function is only mentioned inside the page, while requiring identifying subject matches in results. Lexical screening is conservative and primarily English. It is not semantic verification and can reject valid results or miss some wrong ones. More providers and held-out tasks need qualification.

The independent UI smoke test passed using synthetic transport events: nine Help states, red errors, collapsed nested actions, original-query browser recovery, plain memory explanations, the new favicon, a visible mobile Help button, no overflow at 390 px, reduced motion, and active animation capped at 15 frames/s. This verifies UI wiring, not model task quality.

After the final browser run, only the benchmark's `core` selector was corrected to exclude internet-dependent weather alongside live documentation. That runner-only change does not affect the recorded browser group or production behavior. Source and dependency hashes are retained in each machine-readable report.

## Qualification limits

One Windows 11 x64 Xeon E3-1245 v5 host with 31.9 GiB RAM was used, with four CPU threads and no GPU. The package pins E2B Q4_0, its matching projector, llama.cpp b10809, Node 24.19.0, a 4,096-token context and Q8 K/V. Each final task has one sample; these counts are not a customer reliability estimate.

Physical 4 GB and 8 GB machines, older CPUs, other browsers, ARM64 and other operating systems remain unqualified. Long-task repair, live weather reliability, full process-tree memory/paging measurements, installer recovery/update coverage, signing and commercial release checks remain open. Follow the [benchmark protocol and proposed shipping gates](../BENCHMARKS.md) before declaring support or selling a release. Build and installation checks are recorded separately after packaging.
