# Tom 0.4.0 development evaluation

This build is not a shipping release. Its purpose is to establish a traceable CPU baseline and prevent the specific false completions found during development.

## Changes under evaluation

Tom now sends explicit GBNF to llama.cpp and checks backend enforcement on load. Search requires a real result, followed by relevant successful source reads. Browser arguments, observed URLs and known file hashes can be constrained during decoding. Requested source reads precede file creation. The final reply is checked against current-task evidence; HTTP failures, missing files, rejected writes and failed local-page checks cannot count as completion.

Repairs use the latest verified version of each file, preserve previous bytes, and check the destination before replacement. A named existing output uses its observed hash rather than allowing the model to call it a new file. Character limits and generated-page controls are checked independently. The UI shows actual queries/actions/results, with expandable command and token details.

These mechanisms cannot certify arbitrary natural-language requirements or make the model infallible. File/source requirement detection is currently conservative and primarily English. Lexical relevance is a screen, not semantic fact-checking. Manual quality review and held-out tasks remain necessary.

## Recorded baseline

The [final recorded baseline](baseline-0-4-0.md) passed **5 of 7 planned outcome checks**. It used the final production sources, with hashes recorded in the accompanying JSON. The unrun follow-up now remains in the planned denominator as a failed/skipped case.

| Case | Result | Wall time |
|---|---|---:|
| Exact file creation | Passed; verified bytes and path | 40.8 s |
| Webpage across compaction | Failed; response exceeded its output budget during repair | 591.0 s |
| Follow-up revision | Skipped and counted as failed because the initial webpage task failed | — |
| Two-page browsing | Passed; both observed sources and exact facts | 62.2 s |
| Missing page | Passed negative test; HTTP 404 reported as a blocker | 34.4 s |
| Vision | Passed the single text/shapes fixture using the projector | 30.0 s |
| Live web research | Passed; real search and reads of MDN localStorage and setItem documentation | 211.3 s |

The long task read all three briefs and compacted context four times. Its latest saved page had functioning controls but exceeded the requested character limit. Tom attempted another repair, then the structured response exceeded its generation allowance. The partial response was not executed, and the task did not publish a success claim. This is useful failure containment, **not successful long-horizon performance**. Latency, compact-context repair quality and revision reliability remain release blockers.

An independent UI smoke test passed with synthetic events: search reached the research endpoint; actual actions appeared in nested collapsed details; a blocked task became visibly amber with resume controls; active drawing stayed at 15 frames/s; 390 px width did not overflow; reduced motion stopped animation. This verifies interface wiring and presentation, not model reasoning or task success.

The packaged build passed **50 deterministic tests**, syntax checks on 48 JavaScript files, native compilation, and a fresh portable installation followed by automatic text/tool/recall/vision qualification. See the [package validation record](package-0-4-0.md). The installation test found and corrected a PowerShell decimal-versus-integer manifest bug after the model baseline. That one build-script change is recorded separately; production harness, UI and model configuration remain identical to the baseline. No further model performance result is inferred from packaging checks.

## Measurement limits

The machine is a Windows 11 x64 Xeon E3-1245 v5 with about 32 GB RAM. All inference uses four CPU threads and no GPU. E2B Q4_0, its matching projector, llama.cpp b10809, Node 24.19.0, a 4,096-token context and Q8 K/V are pinned in the reports.

The workstation runs other desktop applications. These are development outcome tests, not controlled latency or energy certification. Temporary folders, tool IDs and local fixture ports vary; full model inputs remain in local journals. Seeds and dependency/source hashes are recorded, but they alone do not make outputs bit-identical. A single repetition is a preliminary baseline, not a reliability percentage for customers.

Supervisor RSS excludes the model and browser processes. Available RAM is a system-wide observation. Physical 4 GB/8 GB machines, older CPU instruction sets, clean Windows variants, ARM64, other OS packages and other browsers remain unqualified. The current result must not be used to advertise universal compatibility.
